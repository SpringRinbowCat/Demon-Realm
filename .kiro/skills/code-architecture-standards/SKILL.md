# 代码与架构标准

本 Skill 是通用标准，不绑定具体产品、模块、玩法、目录、引擎或业务名。项目已有的 README、架构文档、构建配置和代码事实用于确定具体落点；本标准用于约束实现质量和架构边界。若项目规范与本标准有冲突，先说明冲突及影响，不要用局部捷径掩盖结构问题。

## 1. 修改前的架构判断

- 先阅读项目级 README、架构文档和目标类型的 public 头文件，再阅读实现；以接口和实际调用关系为依据，不凭单个函数下结论。
- 对非平凡改动，至少确认：调用方、被调用方、共享状态、事件订阅者、持久化读写方、线程/异步边界和对外 API 影响。
- 先区分实现错误与职责/依赖/数据流问题。若现有结构无法干净地实现需求或根治缺陷，应先调整结构，再实现行为；禁止在错误层持续堆特判。
- 改动应保持最小且聚焦：不得混入无关格式化、顺手重构或不必要的公共 API 扩张。
- 任何项目代码改动都必须在同一次改动中同步修改项目根目录的 `README.md`；根据实际变更更新产品行为、技术架构、模块职责、API、数据流或约束说明。禁止只改代码而不改 README，即使代码变更看似不影响产品行为，也必须在 README 中记录相应变更或同步说明。
- 改变 public API、职责、生命周期、持久化格式或架构关系时，同步更新项目已有的架构/API 文档，并说明兼容性与迁移影响。

## 2. 架构规范

### 2.1 分层与职责

推荐按项目实际情况划分以下职责；名称可以不同，但边界必须清晰：

- **组合根 / 应用入口**：集中创建对象、注入依赖、管理生命周期；业务流程不应散落在多个全局入口。
- **领域模型 / 状态层**：持有业务状态和不依赖外部框架的规则；不持有上层控制器、视图或组合根。
- **Controller / Use Case / Application 层**：编排业务流程、校验命令、调用领域能力；不把展示细节塞进领域模型。
- **Service**：承载跨对象、外部资源或可复用的业务能力；边界应单一，避免变成无边界的万能类。
- **Adapter / Infrastructure 层**：封装平台、网络、文件、第三方库和引擎 API；业务层依赖接口，不直接扩散第三方细节。
- **View / Presentation 层**：负责展示、动画、输入转发和生命周期响应；不持有业务规则，不直接修改不属于自己的业务状态。

一个类应有单一且可描述的主要职责。若类同时负责状态、流程编排、外部 IO 和界面更新，应优先拆分职责或引入明确的协作者。

### 2.2 依赖方向

- 依赖应单向流动，禁止循环依赖。下层不能持有上层具体对象，也不能通过反向 include 或全局查找绕过分层。
- 上层需要下层能力时，优先依赖稳定的接口；下层向上通知使用回调、Delegate、消息或类型化事件，不持有上层对象。
- 依赖注入应在组合根完成。业务单例、静态可变状态和隐藏的全局服务定位器不得控制业务流程；只有无状态基础设施或明确受控的共享资源可采用单例。
- 接口应表达稳定的能力边界，而不是暴露内部数据结构。不要为了避免一次调用就公开可变容器或内部对象。
- 多继承仅用于多个无状态、纯接口契约；带状态的实现优先使用组合和委托。

### 2.3 命令、查询与通知

- 命令通过明确的用例、Controller 或系统接口进入；查询通过只读 API 返回；不要让 View 直接穿透到任意底层对象修改状态。
- 领域通知使用项目统一的事件机制和类型化事件数据；禁止使用无约束的全局字符串事件、框架全局事件或隐藏回调充当业务总线。
- 事件应表达已经发生的事实，不承载隐式命令。订阅者必须可追踪，生命周期结束时取消订阅，避免悬空回调和重复处理。
- 共享状态变化应有唯一的写入边界，避免多个系统同时修改同一字段而无法确定顺序。

### 2.4 数据、持久化与外部服务

- 持久化由统一的存档/数据服务和明确的绑定层管理；禁止各模块散落独立键值、私自序列化或绕过版本迁移机制。
- 读写外部数据时校验版本、缺失字段、范围和失败分支；兼容旧数据时明确默认值、迁移策略和回滚行为。
- 网络、支付、广告、文件、设备和第三方 SDK 等外部能力必须位于 Adapter/Service 边界内；业务层依赖抽象接口，不直接依赖供应商 API。
- 外部回调不能直接穿透到 View 或任意业务对象。先在服务边界完成错误处理、线程切换和状态转换，再通过接口或事件通知上层。

### 2.5 UI、生命周期与线程

- View 只负责展示、动画、输入回传和视图生命周期；规则、数值计算、权限判断和状态变更放在 Model/Controller/Service 等业务层。
- 非主线程不得访问 UI 或非线程安全的共享状态。异步任务完成后，通过明确的调度边界切回拥有对象的线程。
- 对象销毁、卸载或关闭时，必须清理定时器、事件订阅、异步回调、观察者和外部资源；回调不得捕获已失效的 `this`。
- 明确对象所有权与生命周期：拥有关系使用值成员或智能指针，非拥有关系使用引用、指针或观察者语义，并在接口/注释中写清楚。

### 2.6 结构调整与反补丁

以下做法通常表明改动落在错误层，应停止并重新评估架构：

- 在 View 或单个回调中加入业务特判，绕过 Controller/Model/Service。
- 复制相近逻辑、增加临时 flag 或魔法条件，而不是收口到已有规则、配置、Service 或 Effect。
- 用全局变量、业务单例、跨层指针或隐藏事件绕过依赖注入。
- 为修复一个症状而修改共享状态的语义，却没有检查其它调用方、事件订阅、持久化和 UI 使用方。

修复前应写清根因、受影响的调用链和旁路、拟修改的层、公共接口变化及验证方式。若结构确实阻碍正确实现，先补齐接口、调整职责或修正数据流，再实现具体功能。

## 3. C++ 编码规范

### 3.1 命名与命名空间

- 类型、类、文件使用项目既有的大写风格；函数和局部变量使用小驼峰；私有成员使用项目统一的成员后缀或前缀，不在同一项目混用。
- 常量使用统一的 `k` 前缀或项目既有约定；枚举值、模板参数和类型别名保持可读且语义明确。
- 接口可使用 `I` 前缀，但必须在整个项目中保持一致；配置、解析器、存档和适配器使用能表达职责的后缀。
- 业务代码放在明确的命名空间中；禁止 `using namespace`，尤其不能放在头文件中。
- 名称应描述意图而非实现细节；避免缩写、无意义的 `data`/`manager`/`helper` 和带时间性的临时命名。

### 3.2 头文件、依赖与宏

- 遵循“头文件自洽”和“显式依赖”：使用了某个声明就直接 include 对应头文件，不依赖传递 include；能前置声明时避免不必要的重依赖。
- 头文件使用项目统一的 `#pragma once` 或 include guard；不得在头文件中放匿名命名空间、命名空间别名或 `using namespace`。
- include 顺序保持稳定：当前实现对应的头文件、C 标准库、C++ 标准库、第三方库、项目内部头文件；按项目格式化工具执行。
- 普通业务头文件不得随意定义或取消宏。宏应集中在少数基础设施位置；不要用宏切割正式业务逻辑或替代类型安全的常量、函数和模板。
- 调试代码必须有明确的构建边界，不能让调试分支改变正式逻辑或生命周期。

### 3.3 类型、所有权与资源

- 优先使用值语义、RAII 和组合；裸 `new`/`delete` 不得成为常规业务所有权管理方式。
- 只读的大对象、容器和可调用对象优先使用 `const T&`；所有权转移使用移动语义，并避免中间层再次按值复制。
- 指针语义必须明确：可为空时检查并定义失败行为；非拥有指针不得延长对象生命周期；跨异步边界不得保留未经保护的裸指针。
- 保持 const 正确性；只读方法标记 `const`，不暴露可绕过不变量的可变内部引用或指针。
- 禁止 C 风格转换。使用 `static_cast`、`const_cast`、`dynamic_cast` 或 `reinterpret_cast` 时必须有明确理由；慎用运算符重载和用户定义字面量。
- 容器访问、迭代器、数组索引和外部输入必须做边界与有效性校验；配置、网络、存档和第三方返回值必须处理失败分支。

### 3.4 函数、类与表达式

- 函数保持短小、单一职责；约 50 行是需要复查的信号，而不是允许无条件超出的目标。类约 500 行应触发职责拆分评估。
- 控制流优先使用早返回降低嵌套；嵌套通常不超过三层。复杂条件提取为有意义的谓词或领域操作。
- Lambda 必须显式写捕获列表，禁止默认 `[=]`/`[&]`；捕获 `this`、引用和异步对象时确认生命周期。Lambda 仅做局部、清晰的工作，复杂逻辑应提取为命名函数。
- `auto` 用于类型冗长、类型显而易见或迭代器等场景；不会牺牲接口和关键表达式可读性。声明尽量同时初始化，变量保持最小作用域。
- 避免仅靠参数类型/数量区分的脆弱重载、滥用默认参数和复杂的对外模板；公共接口优先稳定、明确、易测试。
- 禁止魔法数和散落字符串；提取为有语义的常量、枚举、配置或规则对象。

### 3.5 注释、API 与版式

- 注释解释约束、原因、所有权、线程要求和非显然的不变量，不重复逐行描述代码。
- 类和 public 方法应写清职责、参数、返回值、错误处理、所有权和线程要求；公共接口变化同步项目文档。
- 类内成员顺序保持一致，建议为：类型别名/嵌套类型、public、protected、private；构造/析构和静态成员遵循项目统一风格。
- 避免无关格式化和全文件重排；历史大文件只修改相关区域，减少 review 噪声和合并冲突。

## 4. 性能与可靠性红线

- 热路径避免不必要的拷贝、分配、解析和 IO；重复创建且生命周期短的对象使用项目已有的池化或复用机制。
- 共享且只读的配置、资源描述和计算结果可使用有明确生命周期的缓存/享元；缓存必须定义失效、线程安全和内存上限。
- 禁止对可变长集合做无意的 O(n²) 扫描。高频查找建立合适的索引，并在数据变更时维护或重建索引。
- 在不改变行为的前提下合并重复条件、移除死分支和重复查找；不要为了表面可读性在帧循环或高频回调中重复线性扫描。
- 性能优化必须以可测量的问题为依据，不能牺牲所有权、线程安全、可测试性或架构边界换取未经验证的微优化。
- 所有外部输入、异步结果和资源加载都要有超时、失败、取消或降级路径；失败不能留下半更新状态或无法回收的资源。

## 5. 交付前架构自检

提交代码前确认：

1. 改动是否位于正确层，依赖方向是否仍然单向，是否引入循环依赖或隐藏全局状态？
2. 是否明确了对象所有权、生命周期、线程边界、错误处理和取消行为？
3. 是否避免了 View 业务化、跨层穿透、业务单例、临时 flag、魔法数和重复逻辑？
4. public API、持久化格式、事件契约或职责变化是否已同步项目文档并考虑兼容性？
5. 是否检查了共享状态的其它读写方、同类事件订阅者、异步回调和相邻功能？
6. 是否保留了必要的验证：编译、静态检查、单元/集成测试或可执行的手工回归步骤？
7. diff 是否只包含本次目标所需的改动，没有无关重构、格式化或调试残留？
