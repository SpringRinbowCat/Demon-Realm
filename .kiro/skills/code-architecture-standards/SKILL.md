# 代码与架构标准

本 Skill 是通用标准，不绑定具体产品、模块、玩法、目录、引擎或业务名。项目已有的 README、架构文档、构建配置和代码事实用于确定具体落点；本标准用于约束实现质量和架构边界。若项目规范与本标准有冲突，先说明冲突及影响，不要用局部捷径掩盖结构问题。

规则分为强制执行和推荐遵守两类。强制规则不满足时不得交付；推荐规则如确需违反，必须在代码注释、评审说明或提交说明中写明原因和影响。

## 1. 修改前的架构判断

- 先阅读项目级 README、架构文档和目标类型的 public 头文件，再阅读实现；以接口和实际调用关系为依据，不凭单个函数下结论。
- 对非平凡改动，至少确认：调用方、被调用方、共享状态、事件订阅者、持久化读写方、线程/异步边界和对外 API 影响。
- 先区分实现错误与职责、依赖、数据流问题。若现有结构无法干净地实现需求或根治缺陷，应先调整结构，再实现行为；禁止在错误层持续堆特判。
- 改动应保持最小且聚焦：不得混入无关格式化、顺手重构或不必要的公共 API 扩张。
- 任何项目代码、配置或资源文件改动都必须在同一次改动中检查另一侧是否存在契约或依赖影响：代码变更要反查配置、资源路径、格式、尺寸、加载、缓存和表现，配置或资源变更要反查读取代码、校验、路径解析、缓存和显示逻辑。根据实际影响同步项目根 README、对应模块 README 或已有架构/API 文档；跨模块变化更新根文档，模块细节更新所属模块文档。禁止只改一侧而留下代码、配置、资源或文档失配；若评估后无需修改另一侧，也应在变更说明或验证中记录该结论。
- 改变 public API、职责、生命周期、持久化格式或架构关系时，同步更新项目已有的架构/API 文档，并说明兼容性与迁移影响。

## 2. 架构规范

### 2.1 分层与职责

推荐按项目实际情况划分以下职责；名称可以不同，但边界必须清晰：

- **组合根 / 应用入口**：集中创建对象、注入依赖、管理生命周期；业务流程不应散落在多个全局入口。
- **领域模型 / 状态层**：持有业务状态和不依赖外部框架的规则；不持有上层控制器、视图或组合根。
- **Controller / Use Case / Application 层**：编排业务流程、校验命令、调用领域能力；不把展示细节塞进领域模型。
- **Service**：承载跨对象、外部资源或可复用的业务能力；边界应单一，避免变成无边界的万能类。
- **Adapter / Infrastructure 层**：封装平台、网络、文件、第三方库和引擎 API；业务层依赖接口，不直接扩散第三方细节。
- **View / Presentation 层**：负责展示、动画、输入转发和生命周期响应；不持有业务规则，不直接修改不属于自己的业务状态。

一个类应有单一且可描述的主要职责。若类同时负责状态、流程编排、外部 IO 和界面更新，应优先拆分职责或引入明确的协作者。

### 2.2 依赖方向与所有权

- 依赖应单向流动，禁止循环依赖。下层不能持有上层具体对象、上层指针或上层回调，也不能通过反向 include 或全局查找绕过分层。
- 上层需要下层能力时，优先依赖稳定的接口；下层向上通知使用回调、Delegate、消息或类型化事件，不持有上层对象。
- 依赖注入应在组合根完成。不得使用单例类或静态可变状态控制业务逻辑；无状态基础设施只有在项目明确允许且生命周期受控时才可共享。
- 接口应表达稳定的能力边界，而不是暴露内部数据结构。不要为了避免一次调用就公开可变容器或内部对象。
- 明确对象所有权与生命周期：拥有关系使用值成员或智能指针，非拥有关系使用引用、指针或观察者语义，并在接口和注释中写清楚。
- 跨异步边界不得保留未经保护的裸指针或已失效对象引用。

### 2.3 命令、查询与通知

- 命令通过明确的用例、Controller 或 System 接口进入；查询通过只读 API 返回；不要让 View 直接穿透到任意底层对象修改状态。
- 领域通知使用项目统一的事件机制和类型化事件数据；禁止使用 Cocos2d-x 内置全局自定义事件系统、无约束的全局字符串事件或隐藏回调充当业务总线。
- 事件应表达已经发生的事实，不承载隐式命令。订阅者必须可追踪，生命周期结束时取消订阅，避免悬空回调和重复处理。
- 共享状态变化应有唯一的写入边界，避免多个系统同时修改同一字段而无法确定顺序。

### 2.4 数据、持久化与外部服务

- 持久化由统一的存档/数据服务和明确的绑定层管理；禁止各模块散落独立键值、私自序列化或绕过版本迁移机制。
- 读写外部数据时校验版本、缺失字段、范围和失败分支；兼容旧数据时明确默认值、迁移策略和回滚行为。
- 网络、支付、广告、文件、设备和第三方 SDK 等外部能力必须位于 Adapter/Service 边界内；业务层依赖抽象接口，不直接依赖供应商 API。
- 外部回调不能直接穿透到 View 或任意业务对象。先在服务边界完成错误处理、线程切换和状态转换，再通过接口或事件通知上层。

### 2.5 UI、生命周期与线程

- View 只负责展示、动画、输入回传和视图生命周期；规则、数值计算、权限判断和状态变更放在 Model、Controller 或 Service 等业务层。
- View 内部禁止启动线程、持有异步句柄或直接管理异步任务；异步工作由 Service 或 Infrastructure 承担。
- 非主线程不得访问 UI 或非线程安全的共享状态。回调入栈前必须由 Service 内部切回主线程，再通知上层。
- 默认在主线程驱动 UI 与大部分逻辑；IO 操作放入 Service 内部的异步接口，并定义错误、取消、超时和生命周期行为。
- 对象销毁、卸载或关闭时，必须清理定时器、事件订阅、异步回调、观察者和外部资源；回调不得捕获已失效的 `this`。

### 2.6 结构调整与反补丁

以下做法通常表明改动落在错误层，应停止并重新评估架构：

- 在 View 或单个回调中加入业务特判，绕过 Controller、Model 或 Service。
- 复制相近逻辑、增加临时 flag 或魔法条件，而不是收口到已有规则、配置、Service 或 Effect。
- 用全局变量、业务单例、跨层指针或隐藏事件绕过依赖注入。
- 为修复一个症状而修改共享状态的语义，却没有检查其它调用方、事件订阅、持久化和 UI 使用方。

修复前应写清根因、受影响的调用链和旁路、拟修改的层、公共接口变化及验证方式。若结构确实阻碍正确实现，先补齐接口、调整职责或修正数据流，再实现具体功能。

## 3. C++ 编码规范

### 3.1 命名与命名空间

以下为强制命名规则：

- 类名、结构体名、枚举类型名和文件名使用大写字母开头的 PascalCase，例如 `MyClass`、`MyClass.h`；项目若统一使用 `.hpp`，则保持项目既有后缀。
- 函数名和变量名使用小驼峰，首字母小写，例如 `doSomething()`、`playerCount`。
- 类的私有成员变量和私有成员方法以 `_` 开头，例如 `_index`、`_updateState()`；同一项目不得混用另一种私有成员命名后缀。
- 常量以小写字母 `k` 开头，例如 `kMaxCount`、`kDefaultSpeed`。
- 业务代码放在明确的命名空间中；非成员函数不得裸露在全局命名空间。
- 禁止使用 `using namespace`，尤其不能放在头文件中。
- 名称应描述意图而非实现细节；避免缩写、无意义的 `data`、`manager`、`helper` 和带时间性的临时命名。

### 3.2 头文件、依赖与宏

以下为强制规则：

- 禁止省略显式 `#include`。使用了某个声明就必须直接 include 对应头文件，不得依赖传递 include；能前置声明时避免不必要的重依赖。
- 头文件必须使用项目统一的 `#pragma once` 或完整的 `#ifndef` 头文件保护。
- 禁止在头文件中使用匿名命名空间、命名空间别名或 `inline namespace`。
- 禁止在业务 `.h`/`.hpp` 文件中定义宏；禁止对已有宏执行 `#undef`。
- 禁止使用宏进行业务条件编译。若构建工具或第三方库强制要求宏，只能集中在构建配置、平台适配或第三方边界，并说明原因，不得扩散到业务头文件。
- 普通业务头文件不得随意定义或取消宏；不要用宏切割正式业务逻辑或替代类型安全的常量、函数和模板。

头文件引用顺序必须保持一致，每类之间使用空行分隔：

1. 当前 `.cpp` 对应的 `.h`/`.hpp` 文件。
2. C 系统库文件。
3. C++ 标准库文件。
4. 第三方库头文件，例如 `cocos2d.h`。
5. 项目内头文件。

### 3.3 类型、继承、转换与运算符

- 优先使用值语义、RAII 和组合；裸 `new`/`delete` 不得成为常规业务所有权管理方式。
- 禁止多重继承；如需复用能力，必须使用组合或委托，接口契约也不得通过多重继承实现。
- 禁止使用非 `public` 继承；需要私有实现复用时，改为将基类实例作为成员对象。
- 禁止使用 C 风格类型转换，统一使用 `static_cast`、`const_cast`、`dynamic_cast` 或 `reinterpret_cast` 等 C++ 风格转换，并为非显然转换写明理由。
- 禁止重载运算符，除非项目明确要求该特定场景并记录原因、语义和测试范围。
- 禁止创建用户定义字面量 `operator""`。
- 容器访问、迭代器、数组索引和外部输入必须做边界与有效性校验。

### 3.4 指针、所有权与 const 正确性

- 指针语义必须明确：可为空时必须在使用前判空，并定义失败行为；非拥有指针不得延长对象生命周期。
- 下层对象禁止持有上层对象的指针、引用或未受控回调。
- 保持 const 正确性；不修改对象状态的成员函数必须声明为 `const`。
- `const` 函数对外暴露指针成员时，必须返回指向 `const` 对象的指针，防止对象穿透和意外修改。
- 不暴露可绕过不变量的可变内部引用或指针；接口设计遵循最小权限原则，避免不必要的修改权限泄漏。
- 所有权转移使用移动语义，并避免中间层重复按值复制；跨线程和异步边界必须明确所有权、取消和失效处理。

### 3.5 函数、表达式、Lambda 与 auto

- 函数保持短小和单一职责；单个函数超过 50 行必须评估并重构拆分。
- 控制流优先使用早返回降低嵌套；函数中的 `if`/`for`/`while` 逻辑不建议超过 3 层，过深应提取子函数。
- 禁止 Lambda 使用默认捕获 `[=]` 或 `[&]`，所有捕获必须显式写出；捕获 `this`、引用和异步对象时必须确认生命周期。
- 禁止对简单类型及可明确表达意图的类型使用 `auto`；只在迭代器等类型冗长或类型确实不适合显式表达时使用。
- 声明变量时应尽量立即初始化并置于最小作用域，避免声明与初始化分离和远离使用位置。
- 禁止魔法数字和散落的业务字符串；必须提取为具名常量、枚举、配置或规则对象。
- 复杂条件应提取为有意义的谓词或领域操作；避免仅靠参数类型或数量区分的脆弱重载。

### 3.6 注释、接口与成员声明顺序

- 每个类必须在声明处添加注释，清晰描述类的功能、职责和使用场景。
- 类的成员变量和 public 方法必须添加注释；方法注释说明用途、参数、返回值、错误处理、所有权和线程要求。
- public API、持久化格式、事件契约和职责变化必须同步项目文档，并说明兼容性、迁移和失败行为。
- 类内成员声明顺序统一为：类型定义；public、protected、private 访问区；每个访问区内构造/析构函数优先于其它函数，静态成员先于非静态成员，函数先于变量。
- 类型别名、嵌套类型和枚举等类型定义放在类声明的最高优先级位置。
- 避免无关格式化和全文件重排；历史大文件只修改相关区域，减少 review 噪声和合并冲突。

### 3.7 Cocos2d-x 生命周期、内存与线程

- Cocos `Scene`、`Node`、`Sprite`、动画和触摸监听只属于 Presentation 层；Domain/Model 不得包含 Cocos 头文件，也不得持有 Cocos 节点指针。
- Cocos `Ref`/`Node` 对象优先使用项目约定的 `static create()` 创建，并使用匹配的引用计数生命周期；不应对受 Cocos 管理的对象使用普通 `delete`。
- 非节点树管理的 Cocos 对象需要手动 `retain()` 时，必须在明确的生命周期结束点配对 `release()`；禁止泄漏或重复释放。
- 移除节点时必须清理定时器、事件监听、异步回调和其它引用关系，防止对象销毁后仍被访问。
- `GameViewAdapter` 或 `GameViewLayout` 集中解析业务挂载点，避免业务代码散落 `getChildByName()` 和硬编码坐标。
- View 内禁止启动线程或持有异步句柄。IO 操作放入 Service 内部的异步接口，回调入栈前由 Service 切回主线程；非主线程禁止操作 UI。
- 像素贴图由 `PixelAssetRepository`、`PixelSpriteView` 或同职责资源模块统一管理；贴图只负责表现，不参与伤害、金币、升级和关卡规则计算。

### 3.8 防御性编程与外部输入

- 外部输入、配置数据、网络回调、文件读取和第三方返回值必须做合法性校验，并定义缺失、越界、失败、取消和超时行为。
- 数组、容器和迭代器访问必须做越界和失效检查，不能依赖调用方恰好传入合法值。
- 读写外部数据时校验版本、缺失字段和范围；兼容旧数据时明确默认值、迁移策略和回滚行为。
- 失败不能留下半更新状态、泄漏对象或无法回收的异步任务。

### 3.9 不建议事项

以下做法不是默认方案；如确需使用，应在代码注释、评审说明或提交说明中写明理由：

- 不建议使用类的静态成员函数仅做作用域划分；静态方法应与该类的实例或静态数据存在明确关系。
- 不建议仅因参数类型不同就使用函数重载，优先在函数名中体现参数信息。
- 不建议仅因同类型参数数量不同就使用函数重载，优先使用容器参数，例如 `std::vector`。
- 不建议使用缺省参数，优先考虑明确的函数重载或拆分用例。
- 不建议 Lambda 函数体超过 5 行；过长应改为具名函数。
- 不建议编写复杂模板代码；使用模板时应最小化复杂度，避免对外暴露模板实现细节。
- 不建议使用预处理宏，优先使用内联函数、枚举和具名常量替代。
- 不建议让函数嵌套超过 3 层逻辑；过深应提取子函数。
- 不建议为了方便而引入单例类控制逻辑、全局可变状态或隐藏服务定位器。

### 3.10 代码规模与可维护性

- 单个类超过 500 行必须评估职责拆分和重构。
- 模块职责必须明确，遵循单一职责原则；代码须具备可维护性和可扩展性。
- 只有具备独立职责、生命周期或存档边界的能力才拆成独立模块；不要为了模仿大型项目而过早拆分。

## 4. 性能与可靠性红线

- 热路径避免不必要的拷贝、分配、解析和 IO；重复创建且生命周期短的对象使用项目已有的池化或复用机制。
- 共享且只读的配置、资源描述和计算结果可使用有明确生命周期的缓存或享元；缓存必须定义失效、线程安全和内存上限。
- 禁止对可变长集合做无意的 O(n²) 扫描。高频查找建立合适的索引，并在数据变更时维护或重建索引。
- 在不改变行为的前提下合并重复条件、移除死分支和重复查找；不要为了表面可读性在帧循环或高频回调中重复线性扫描。
- 性能优化必须以可测量的问题为依据，不能牺牲所有权、线程安全、可测试性或架构边界换取未经验证的微优化。
- 所有外部输入、异步结果和资源加载都要有超时、失败、取消或降级路径；失败不能留下半更新状态或无法回收的资源。

## 5. 交付前架构自检

提交代码前确认：

1. 改动是否位于正确层，依赖方向是否仍然单向，是否引入循环依赖或隐藏全局状态？
2. 是否明确了对象所有权、生命周期、线程边界、错误处理、取消行为和 Cocos 引用计数配对？
